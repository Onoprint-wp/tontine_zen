## 1. PRÉSENTATION DU PROJET ET CONTEXTE

### 1.1. Contexte et Problématique

Au Cameroun, la tontine est une pratique sociale et économique majeure. Pourtant, elle souffre de fragilités structurelles :

- **Manque de transparence** : Les comptes sont souvent tenus manuellement, sans visibilité pour tous.
- **Risque d'impayés** : Un membre peut cesser de payer sans conséquence grave.
- **Absence de cadre juridique** : En cas de litige, les recours sont quasi inexistants.
- **Méfiance numérique** : Les solutions existantes (Djangui, yaNkap) n'apportent pas de garantie suffisante contre les défauts de paiement.

### 1.2. Notre Réponse : « TONTINE ZEN LIGHT »

Nous développons une **application mobile de gestion de tontine** qui repose sur **trois piliers** :

| Pilier | Bénéfice |
| :--- | :--- |
| **Transparence totale** | Historique des paiements consultable par tous |
| **Réputation publique** | Un score de confiance (0-100) visible pour chaque membre |
| **Cadre juridique simple** | Un contrat OHADA signé électroniquement |

> **Nous ne touchons pas à l'argent.** Les paiements se font hors application (Mobile Money, espèces). Notre valeur ajoutée est la **confiance** et la **transparence**.

### 1.3. Positionnement

« TONTINE ZEN LIGHT » est une **application communautaire** qui transforme la tontine informelle en un espace de confiance numérique. Elle se différencie de Djangui par :

- L'absence de frais de transaction (modèle freemium).
- Un **score de réputation** public, qui est un puissant mécanisme de pression sociale.
- Un **contrat juridique** exécutoire.

## 5. PARCOURS UTILISATEUR (UX)

### 5.1. Inscription

1. L'utilisateur saisit son numéro de téléphone.
2. Reçoit un code de validation par SMS.
3. Remplit son profil (nom, prénom, photo).
4. **Le compte est actif immédiatement** (pas de KYC lourd).

### 5.2. Création d'une Tontine

1. L'utilisateur clique sur "Créer une tontine".
2. Remplit le formulaire (nom, montant, fréquence, etc.).
3. Invite les membres (par WhatsApp/SMS).
4. Les membres reçoivent le lien, s'inscrivent et rejoignent le groupe.
5. Une fois tous les membres inscrits, le contrat est généré et signé par tous.

### 5.3. Paiement d'une Cotisation (Hors App)

1. Le membre reçoit une notification de rappel.
2. Il paie **en espèces** au trésorier ou via **Mobile Money** (transfert direct, pas via l'app).
3. Il confirme le paiement dans l'application (ou le trésorier le fait).
4. L'application enregistre la transaction et met à jour le score du membre.

### 5.4. Tirage

1. Le bénéficiaire est désigné (automatiquement ou par vote).
2. Le trésorier **verse les fonds** au bénéficiaire (hors app).
3. Le bénéficiaire confirme la réception dans l'application.

### 6.1. Stack Technologique

| Composant | Technologie |
| :--- | :--- |
| Frontend (Mobile) | Flutter (iOS/Android) |
| Backend | Node.js + Express |
| Base de données | PostgreSQL |
| Cache | Redis |
| Hébergement | AWS / OVH (Cameroun) |
| Notifications | Firebase FCM + Twilio (SMS) |
| Signature électronique | YouSign / DocuSign |

### 6.2. Intégrations Externes

| Service | API | Utilisation |
| :--- | :--- | :--- |
| Signature électronique | YouSign | Signature des contrats |
| Notifications SMS | Twilio | Envoi de rappels par SMS |
| WhatsApp | WhatsApp Business API | Envoi de rappels et notifications |
| Google Analytics / Firebase | Firebase Analytics | Suivi des utilisateurs |

### 6.3. Sécurité

| Couche | Mesure |
| :--- | :--- |
| Données en transit | HTTPS (TLS 1.3) |
| Mots de passe | Hashé avec bcrypt |
| Authentification | JWT avec expiration courte (15 min) |
| Sécurité des APIs | Rate limiting, validation stricte des entrées |

## 3. USER FLOWS (Parcours Clés)

### 3.1. Inscription

1. L'utilisateur ouvre l'application.
2. Écran d'accueil : "Rejoignez la communauté ZEN !".
3. Saisie du numéro de téléphone.
4. Validation du code par SMS (automatique ou manuel).
5. Formulaire : nom, prénom, photo (optionnelle).
6. **Compte actif immédiatement** (pas de KYC lourd).
7. **Feedback** : "Félicitations ! Vous êtes prêt(e) à créer ou rejoindre une tontine."

### 3.2. Création d'une Tontine

1. L'utilisateur clique sur le bouton "+" (flottant en bas à droite).
2. Remplit le formulaire (nom, montant, fréquence, nombre de membres, type).
3. Clique sur "Créer".
4. L'application génère un **lien d'invitation**.
5. L'utilisateur partage le lien via WhatsApp, SMS, ou email.
6. Les membres cliquent sur le lien, s'inscrivent (si pas encore) et rejoignent la tontine.
7. **Dès que tous les membres sont inscrits** :
    - L'application génère le **contrat OHADA** en PDF.
    - Chaque membre signe électroniquement.
    - La tontine est officiellement active.
8. **Feedback** : "Tontine créée avec succès ! Le premier tour commencera le [date]."

### 3.3. Paiement d'une Cotisation (Hors App)

1. Le membre reçoit une **notification push** : "Cotisation de [X] FCFA due dans 24h."
2. Il paie **hors application** (espèces au trésorier ou transfert Mobile Money).
3. **Le trésorier** ouvre l'application, va dans la tontine, et clique sur "Confirmer le paiement" pour le membre concerné.
4. L'application met à jour le statut du membre : "Payé".
5. **Impact** : Le **score de réputation** du membre augmente.
6. **Notification** : "Paiement confirmé pour [Nom]."

### 3.4. Tirage (Réception des Fonds)

1. À la date prévue, l'application **calcule automatiquement** le bénéficiaire (tirage aléatoire ou ordre fixe).
2. Une notification est envoyée à tous les membres : "Le bénéficiaire du tour est [Nom]."
3. Le **trésorier** verse les fonds au bénéficiaire (hors application).
4. Le bénéficiaire confirme la réception dans l'application.
5. **Feedback** : "Tirage validé. Prochain tirage le [date]."

### 3.5. Signalement d'un Litige

1. L'utilisateur va dans la tontine, section "Litige".
2. Sélectionne le type (impayé, désaccord, comportement).
3. Décrit le problème (texte libre).
4. Sélectionne un médiateur dans la liste proposée.
5. L'application notifie le médiateur et crée un espace de médiation sécurisé (chat).
6. Le médiateur échange avec les parties et propose une solution.
7. Une fois la résolution acceptée, le litige est clôturé.
8. **Feedback** : "Litige clôturé. Merci d'avoir utilisé la médiation ZEN."

## 1. OBJECTIF

Ce document définit l'architecture technique, les choix technologiques, et les exigences de sécurité et de performance.

---

## 2. CHOIX TECHNOLOGIQUES

### 2.1. Frontend (Application Mobile)

| Composant | Technologie | Justification |
| :--- | :--- | :--- |
| Framework | Flutter (Dart) | Multiplateforme iOS/Android à partir d'un seul codebase |
| État | Provider ou Riverpod | Gestion d'état simple et performante |
| Réseau | `http` ou `Dio` | Appels API RESTful |
| Stockage local | SharedPreferences | Stockage des tokens et préférences utilisateur |

### 2.2. Backend (API)

| Composant | Technologie | Justification |
| :--- | :--- | :--- |
| Langage | Node.js (TypeScript) | Léger, rapide, écosystème riche |
| Framework | Express.js | Framework minimalist pour APIs |
| Authentification | JWT (JSON Web Tokens) | Sessions sans état, adaptées aux mobiles |
| Validation | Joi ou Zod | Validation stricte des entrées |

### 2.3. Base de Données

| Composant | Technologie | Justification |
| :--- | :--- | :--- |
| Base principale | PostgreSQL | Relationnelle, ACID, fiable |
| Cache | Redis | Gestion des sessions, notifications, mise en cache |
| Stockage de fichiers | AWS S3 / OVH | Contrats PDF, photos de profil |

### 2.4. Infrastructure (Hébergement)

| Composant | Choix | Justification |
| :--- | :--- | :--- |
| Cloud | AWS (région Afrique du Sud) ou OVH (France) | Proximité, souveraineté des données |
| Serveur | EC2 (ou ECS pour conteneurs) | Scalable |
| Base de données | RDS (PostgreSQL) | Géré et sauvegardé automatiquement |
| Cache | ElastiCache (Redis) | Performance |
| Stockage | S3 | Contrats, photos |
| CDN | CloudFront | Accélération des assets |

---

## 3. ARCHITECTURE DU SYSTÈME

```
[Application Mobile (Flutter)]
         │
         ▼
  [API Gateway (Nginx)]
         │
         ▼
[Backend API (Node.js/Express)]
         │
         ├─────────────── [Base de Données PostgreSQL]
         │
         ├─────────────── [Cache Redis]
         │
         ├─────────────── [Service Signature Électronique (YouSign)]
         │
         ├─────────────── [Service Notifications (Firebase FCM + Twilio)]
         │
         └─────────────── [Stockage S3/OVH]
```

### 3.1. Flux de Données (Exemple : Confirmation d'un Paiement)

1. Le trésorier ouvre l'application et appuie sur "Confirmer le paiement".
2. Le frontend envoie une requête POST à `/api/payments/confirm` avec `member_id` et `tontine_id`.
3. Le backend :
    - Vérifie que l'utilisateur est autorisé (trésorier ou membre du groupe).
    - Met à jour le statut du paiement dans la table `transactions`.
    - Calcule et met à jour le score de réputation du membre.
    - Envoie une notification push à tous les membres.
4. Le frontend affiche une confirmation et met à jour le tableau de bord.
5. **Temps de réponse cible** : < 300ms.

## 4. MODÉLISATION DE LA BASE DE DONNÉES (UML)

### Tables Principales

| Table | Champs clés |
| :--- | :--- |
| **`users`** | `id`, `phone_number`, `first_name`, `last_name`, `photo_url`, `reputation_score`, `is_premium`, `created_at` |
| **`tontines`** | `id`, `name`, `amount`, `frequency`, `type`, `status`, `contract_url`, `created_at` |
| **`tontine_members`** | `id`, `tontine_id`, `user_id`, `role` (admin/member), `joined_at`, `signature_status` |
| **`transactions`** | `id`, `tontine_id`, `user_id`, `type` (cotisation/tirages), `amount`, `status` (paid/late), `confirmed_at` |
| **`reputation_events`** | `id`, `user_id`, `event_type` (paiement/retard/litige), `score_delta`, `created_at` |
| **`disputes`** | `id`, `tontine_id`, `reporter_id`, `defendant_id`, `mediator_id`, `description`, `status`, `resolution` |
| **`mediators`** | `id`, `user_id`, `expertise`, `availability`, `rating` |

---

## 5. SÉCURITÉ

| Couche | Mesure |
| :--- | :--- |
| Données en transit | HTTPS avec TLS 1.3 |
| Données sensibles | Chiffrement AES-256 (base de données, S3) |
| Mots de passe | Hashés avec bcrypt (coût 12) |
| Authentification | JWT (expiration 15 min) + Refresh Token |
| 2FA | Optionnel (pour les transactions > 500 000 FCFA) |
| Rate Limiting | 100 requêtes/minute par IP |
| Validation des entrées | Zod ou Joi (prévention injection SQL/XSS) |
| Logs | Audit des accès (qui, quand, quelle action) |

---

## 6. INTÉGRATIONS EXTERNES

| Service | API | Utilisation |
| :--- | :--- | :--- |
| YouSign | API YouSign | Signature électronique des contrats |
| Twilio | API Twilio | Envoi de SMS (notifications, rappels) |
| Firebase | FCM (Firebase Cloud Messaging) | Notifications push |
| WhatsApp | WhatsApp Business API | Envoi de rappels et notifications (optionnel) |

---

## 7. PERFORMANCES ET SCALABILITÉ

- **Temps de réponse** : < 300ms pour 95% des requêtes.
- **Montée en charge** : Architecture horizontale (possibilité d'ajouter des instances backend) avec un load balancer.
- **Cache** : Mise en cache des données fréquentes (ex: scores de réputation) dans Redis.
- **Indexation** : Indexer `user_id`, `tontine_id`, `status` dans les tables.

La plateforme n'est pas responsable des impayés entre membres. Elle fournit un cadre de transparence et de médiation.

ARTICLE 3 : DONNÉES PERSONNELLES
Les données collectées sont utilisées uniquement dans le cadre du service. L'utilisateur peut demander la suppression de ses données à tout moment.

ARTICLE 4 : RÉSILIATION
L'utilisateur peut supprimer son compte à tout moment.

Ce document définit la stratégie de test pour garantir la fiabilité, la sécurité et la performance de l'application avant le lancement.

---

## 2. TYPES DE TESTS

### 2.1. Tests Unitaires
- **Objectif** : Vérifier chaque petite fonction (ex: calcul d'un score de réputation).
- **Outil** : Jest (JavaScript) pour le backend.
- **Cible** : 80% de couverture de code minimum.

### 2.2. Tests d'Intégration
- **Objectif** : Vérifier que les modules interagissent correctement (ex: l'API de paiement communique bien avec la base de données).
- **Outil** : Supertest, Postman, ou scripts automatisés.

### 2.3. Tests Fonctionnels (End-to-End)
- **Objectif** : Simuler le parcours complet d'un utilisateur (ex: inscription, création de tontine, paiement, tirage).
- **Outil** : Cypress ou Appium.
- **Environnement** : Serveur de test dédié (staging).

### 2.4. Tests de Performance
- **Objectif** : Vérifier le comportement de l'application sous charge (ex: 1 000 utilisateurs simultanés).
- **Outil** : Apache JMeter ou K6.
- **Métriques** : Temps de réponse < 300ms, taux d'erreur < 1%.

### 2.5. Tests de Sécurité
- **Objectif** : Identifier les vulnérabilités (OWASP Top 10).
- **Outil** : OWASP ZAP, Burp Suite.
- **Points clés** : Injections SQL, XSS, authentification, contrôle d'accès.

### 2.6. Tests d'Acceptation Utilisateur (UAT)
- **Objectif** : Valider l'application avec un groupe pilote de 50 utilisateurs réels (bêta-test).
- **Méthode** : TestFlight pour iOS, Google Play Console pour Android.
- **Feedback** : Recueillir les retours via un formulaire in-app.

# 🔍 Logique et Questionnement : La Méthode pour TONTINE ZEN

Le principe de logique et le questionnement stratégique sont **les deux faces d'une même pièce** : le questionnement pose les bonnes questions, la logique y apporte des réponses rationnelles basées sur des faits.

Voici comment cette méthode s'applique concrètement à votre projet **« TONTINE ZEN LIGHT »**.

---

## 🧠 La Boucle Vertueuse : Questionner → Logiquer → Décider

```
[QUESTIONNER]
    │
    ├── "Est-ce vraiment nécessaire ?"
    ├── "À quel prix ?"
    ├── "Quels sont les risques ?"
    ├── "Que disent les faits ?"
    │
    ▼
[LOGIQUER] (Analyser avec les 4 piliers)
    │
    ├── Objectivité (faits, données, lois)
    ├── Coût/Bénéfice (est-ce rentable ?)
    ├── Réduction des risques (est-ce maîtrisable ?)
    ├── Adaptabilité (peut-on itérer ?)
    │
    ▼
[DÉCIDER]
    │
    ├── Faire / Ne pas faire
    ├── Maintenant / Plus tard
    ├── Comment (simplifié ou complexe)
```

## 📌 Application concrète : Les 5 grandes questions clés du projet

### Question 1 : Le séquestre bancaire est-il indispensable dès la V1 ?

| Étape | Analyse |
| :--- | :--- |
| **Questionnement** | "Est-ce que je peux lancer sans séquestre ? Les utilisateurs vont-ils me faire confiance ?" |
| **Logique (Objectivité)** | Les études BEAC (2023) montrent que les utilisateurs sont prêts à payer max 0,8% de frais. Le séquestre coûte 1,5%. Donc économiquement non viable. |
| **Logique (Coût/Bénéfice)** | Séquestre en V1 = 40M FCFA de dev + 12 mois de délai + risque COBAC. Bénéfice = sécurité des fonds. Mais 80% des tontines sont < 500 000 FCFA. Le coût est supérieur au bénéfice. |
| **Logique (Risque)** | Risque réglementaire (agrément 500M capital) = très élevé. Risque de rejet utilisateur (prix trop élevé) = élevé. |
| **Logique (Adaptabilité)** | On peut ajouter le séquestre en V3, une fois la base utilisateurs prouvée. |
| **Décision logique** | **REPORTER le séquestre à la V3.** |

---

### Question 2 : Faut-il cibler tout le Cameroun ou seulement les grandes villes ?

| Étape | Analyse |
| :--- | :--- |
| **Questionnement** | "Pourquoi se limiter aux villes ? Les ruraux ont aussi besoin de tontines." |
| **Logique (Objectivité)** | 85% des utilisateurs de Mobile Money sont en zone urbaine (ANTIC, 2024). Les ruraux utilisent le Mobile Money pour recevoir, pas pour des opérations complexes. |
| **Logique (Coût/Bénéfice)** | Cibler les ruraux en V1 = coût marketing élevé (radio locale, agents) pour un taux d'adoption faible. Cibler les urbains = coût maîtrisé (influenceurs, bouche-à-oreille) pour un taux d'adoption élevé. |
| **Logique (Risque)** | Lancer en zone rurale sans infrastructure numérique = risque d'échec élevé. |
| **Logique (Adaptabilité)** | On peut étendre aux zones rurales en V2/V3, via les agents de proximité. |
| **Décision logique** | **SE LIMITER à Douala, Yaoundé, Bafoussam en V1.** |

---

### Question 3 : Faut-il monétiser par frais de transaction ou par abonnement ?

| Étape | Analyse |
| :--- | :--- |
| **Questionnement** | "Les frais de transaction sont-ils acceptables ?" |
| **Logique (Objectivité)** | Une étude de la BEAC (2023) montre que les Camerounais comparent le coût de la tontine digitale à la tontine informelle (gratuite). Tout frais perçu est perçu comme une perte. |
| **Logique (Coût/Bénéfice)** | Frais de transaction = 1% sur 500 000 FCFA = 5 000 FCFA. L'utilisateur voit ça comme "perte". Abonnement = 2 000 FCFA/mois = "service rendu". Perception différente. |
| **Logique (Risque)** | Frais de transaction = risque de rejet massif. Abonnement = risque plus faible (l'utilisateur paie pour un service, pas pour une transaction). |
| **Logique (Adaptabilité)** | On peut commencer par le freemium (gratuit + premium), et ajouter des frais de transaction plus tard pour les fonctionnalités avancées. |
| **Décision logique** | **ADOPTER le modèle Freemium** (gratuit + abonnement Premium). |

---

### Question 4 : Faut-il demander un agrément COBAC dès le départ ?

| Étape | Analyse |
| :--- | :--- |
| **Questionnement** | "Ne vaut-il pas mieux être en règle dès le départ ?" |
| **Logique (Objectivité)** | Le capital minimum pour un "Établissement de Monnaie Électronique" est de 500M FCFA (COBAC 2024/01). Vous n'avez pas ce capital. |
| **Logique (Coût/Bénéfice)** | Demander l'agrément en V1 = 18 mois de procédures + coûts juridiques élevés + immobilisation de fonds. Bénéfice = conformité. Mais vous n'avez pas encore de revenus. |
| **Logique (Risque)** | Risque de refus = très élevé. Risque de retard = très élevé. |
| **Logique (Adaptabilité)** | Passer par une banque partenaire (qui a déjà l'agrément) en V2, puis demander l'agrément en V3. |
| **Décision logique** | **NE PAS DEMANDER l'agrément en V1.** Passer par un partenaire bancaire en V2, et demander l'agrément en V3. |

---

### Question 5 : Faut-il intégrer l'assurance dès la V1 ?

| Étape | Analyse |
| :--- | :--- |
| **Questionnement** | "L'assurance est une fonctionnalité clé. Pourquoi ne pas la lancer ?" |
| **Logique (Objectivité)** | L'assurance nécessite des données pour calculer la sinistralité. Sans données, les primes seront mal calibrées (trop chères ou insuffisantes). |
| **Logique (Coût/Bénéfice)** | Intégrer l'assurance en V1 = coût de développement + négociation avec un assureur + risque de mauvais pricing. Bénéfice = fonctionnalité attractive. |
| **Logique (Risque)** | Risque de sinistres non couverts (si primes trop basses) = risque de réputation. |
| **Logique (Adaptabilité)** | Lancer l'assurance en V1.5, une fois que vous avez des données sur le comportement des utilisateurs (taux de retard, litiges). |
| **Décision logique** | **REPORTER l'assurance à la V1.5** (6 mois après le lancement). |

| # | Question | Décision logique | Justification |
| :--- | :--- | :--- | :--- |
| 1 | Séquestre en V1 ? | **NON** (reporté à V3) | Coût > bénéfice, risque COBAC, utilisateurs pas prêts |
| 2 | Cibler tout le Cameroun ? | **NON** (seulement Douala/Yaoundé/Bafoussam) | Adoption faible en zone rurale en V1 |
| 3 | Frais de transaction ? | **NON** (modèle Freemium) | Frais perçus comme une perte, abonnement perçu comme un service |
| 4 | Agrément COBAC en V1 ? | **NON** (partenariat bancaire en V2) | Capital 500M FCFA impossible en V1 |
| 5 | Assurance en V1 ? | **NON** (reportée à V1.5) | Pas de données pour calibrer les primes |

## 💎 LA RÈGLE D'OR

> **En logique de projet, "FAIRE" n'est pas toujours la bonne réponse.**
> 
> La vraie question n'est pas "peut-on le faire ?", mais **"faut-il le faire maintenant, et à quel prix ?"**

**Ce que la logique t'a appris pour TONTINE ZEN** :

- Le séquestre est une bonne idée, mais **au mauvais moment**.
- L'assurance est une bonne idée, mais **au mauvais moment**.
- L'agrément COBAC est une bonne idée, mais **au mauvais moment**.
- Les zones rurales sont un bon marché, mais **au mauvais moment**.

**La logique ne dit pas "renonce". Elle dit "attends le bon moment".**

> **Et le bon moment, c'est quand tu as prouvé que les utilisateurs veulent ton service de base (V1), que tu as des données (V1.5), que tu as une base d'utilisateurs solide (V2), et que tu as les moyens (V3).**

---

**Cette méthode de questionnement logique est désormais votre boussole** pour chaque décision future. Applique-la à chaque nouvelle fonctionnalité, chaque nouveau marché, chaque nouveau partenariat.

## 3. INTÉGRATION DETAILÉE : YOUSIGN (Signature Électronique)

### 3.1. Objectif
Permettre aux membres de signer électroniquement le contrat de tontine généré par l'application.

### 3.2. Protocole
- **Type** : REST API (synchrone)
- **Authentification** : API Key (avec secret)
- **URL de base** : `https://api.yousign.com/v3`

### 3.3. Flux de Données

1. L'application génère un contrat en PDF.
2. L'application envoie une requête POST à l'API YouSign pour créer une demande de signature.
3. YouSign renvoie un lien de signature.
4. L'application envoie le lien à chaque membre (via notification/SMS).
5. Le membre clique sur le lien, signe sur l'interface YouSign.
6. YouSign envoie un webhook (ou l'application interroge régulièrement le statut).
7. Lorsque tous les membres ont signé, l'application met à jour le statut de la tontine.

### 3.4. Exemple de Requête

```json
POST /api/v3/signature_requests
Headers: { "Authorization": "Bearer <API_KEY>" }
Body: {
  "name": "Contrat Tontine des sœurs",
  "documents": [
    {
      "document_id": "123",
      "file": "base64_encoded_pdf"
    }
  ],
  "signers": [
    { "email": "ngo@example.com", "name": "Ngo" }
  ]
}
```

| Partie | Responsabilité |
| :--- | :--- |

- **URL de base** : `https://api.twilio.com/2010-04-01`

### 4.3. Flux de Données

2. Twilio traite la demande et envoie le SMS.
3. Twilio retourne un statut (que l'application peut interroger via webhook).

### 4.4. Exemple de Requête

## 4. PROCÉDURE DE SIGNALEMENT DES ANOMALIES

1. Un testeur identifie un bug.
2. Il le signale dans l'outil de gestion de projet (ex: Jira, GitHub Issues).
3. Le bug est priorisé :
    - **P0** : Bloquant (application inutilisable) → Correction immédiate.
    - **P1** : Majeur (fonctionnalité importante non fonctionnelle) → Correction dans les 24h.
    - **P2** : Mineur (défaut d'affichage, texte) → Correction avant la mise en production.
4. Le développeur corrige le bug.
5. Le testeur vérifie la correction.
6. Le bug est marqué "Résolu".
